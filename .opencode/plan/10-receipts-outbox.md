# 10. Receipts and outbox

In an office you hand a document to a clerk and receive a stamped receipt.
Nothing is filed until the registry files it. oxkv makes that model literal. A
replica holds a tray of intents. An intent leaves the tray only with a verdict.
The verdict and the filed data become true together, or not at all.

## What the greater goal demands

The authority owns truth and serializes writes. The replica is read-only. A
client never writes. A write is a request with an idempotency key and a base
version, and the authority answers with a receipt in one of four states.

**Offline first** requires the outbox to be durable replica state, not a process
buffer. **Query as the unit of ownership** requires an intent not to be data, or
get and search disagree about what is present. **One shard, one transaction**
requires data, index, receipt, audit, and event to commit together at one
version.

A 1.0 contract adds a fourth demand. C5 (receipt and error semantics) and A3 (event envelope) become public surface
at 1.0. State names, reason codes, error strings, and receipt bytes must be few,
named, stable, and vector-tested.

## Required capabilities

1. **Durable outbox.** Record identity, payload digest, payload, base version,
   target shard, and dependency edges before the first send.
2. **Stable identity.** Choose it before the first attempt, and use it in the
   outbox, on the wire, in the ledger, and in the receipt.
3. **Closed state set.** `Queued`, `Committed`, `Rejected`, `Conflict`, with one
   source and three sinks.
4. **Idempotent submit.** A retry returns the recorded outcome and applies
   nothing.
5. **Acknowledgement.** Report that a terminal outcome is held durably and will
   not be resent.
6. **Retention.** Keep a receipt until no legal retry can arrive, then compact the
   payload to a digest.
7. **Atomicity.** The authority commits data, index, receipt, audit, and event
   together. The replica commits outbox removal, receipt append, and the
   acknowledgement marker together.
8. **Visibility.** The receipt carries `commit_version`, the replica exposes
   `applied_version`, and the application has a display contract.

## Invariants that must hold

- **I1.** No byte leaves the replica before the intent is durable locally.
- **I2.** An identity never changes and never names two payloads.
- **I3.** State moves only along the declared graph. Only the authority writes a
  verdict about data.
- **I4.** A terminal receipt is immutable. A repeat submit returns the same
  state, `commit_version`, and reason, byte for byte.
- **I5.** One verdict, one `commit_version`. The receipt `commit_version` equals the `commit_version` at
  which the data and the index entry become readable.
- **I6.** A replica never claims local visibility before it applies the committed
  `commit_version`.
- **I7.** A pending intent is never scope data. Get does not return it, search
  does not match it, and a count does not include it.
- **I8.** Retention exceeds the replay horizon. No collection step deletes a
  receipt that a legal retry can still reach.
- **I9.** `Conflict` closes one intent. Reconciliation is a new intent with a new
  identity and a higher base version.

## Decisions and technical choices

### The replica chooses the identity

An authority-assigned identity fails offline. The client could not name its own
intent before the network answered, so the outbox would hold anonymous records.
This design uses a 128-bit key generated by the replica and scoped to the
authenticated client. Reuse with a different
payload digest returns `write.idempotency_key_reuse`. Reuse with the same digest is a
retry.

### A receipt is a record, not an overlay

An overlay puts a pending flag on the row or a shadow row beside it. It gives one
key two versions in one snapshot and forces get, search, and the pagination
cursor to agree on a version. It also puts unvalidated data in the scope and
makes replica state depend on local write history.

The receipt is a separate record in the `0x01` receipt system sub-namespace of the shard that owns the
key. It commits with the data and reads in one shard lookup. It is not a scope
and not replicated as scope data. The scope holds authority-projected data and
nothing else.

### A queued write is a receipt, never pending data

A queued write appears to the user as a receipt in state `Queued`, not as a row.
The application may show the intent text, target, base version, and state. It may
not show the intent as a list record, a search hit, or a count.

A labelled preview is permitted only in a separate view that is not the scope. It
is discarded on `Rejected` and `Conflict` and is never indexed or stored in scope
storage. The default is stricter: render the receipt, not a ghost row.

### Three terminal states, one live state

A receipt has four lifecycle states. `Queued` is live and not terminal.
`Committed`, `Rejected`, and `Conflict` are terminal.

`Conflict` is terminal for the intent, not for the user's goal. The receipt
records the `base_version` it was checked against and the `key_version` that won.
Reconciliation is a new intent that names the old one in `supersedes`.

### Retention is derived, not guessed

Retention is a manifest-declared horizon. The authority keeps a terminal receipt
for at least `max_outbox_age + max_ack_delay + margin`. The replica keeps its
entry until the authority confirms the acknowledgement, then for an audit
window. Compaction replaces the payload with a digest and keeps identity, state,
version, and reason.

`receipt.expired` says the outcome is unknown and the client must re-read at a
pinned `commit_version`. An identity the authority never saw returns `receipt.not_found`,
which is safe to submit again, because verdict and data commit atomically. A full
outbox returns `outbox.full` and refuses the new intent. It never drops the oldest
queued intent.

### The client may close its own intent

A user can cancel before a verdict arrives. The client marks the local outbox
entry `CancelRequested`, then `Abandoned`, in the transaction that removes it. A
local state is not a receipt. The client must not write `Rejected`. A late
authority verdict wins for the data. If the authority commits after a local
cancel, the receipt is `Committed`.

### Time, randomness, and the wire

Timestamps are metadata, passed in as a parameter, and policy never compares
them. Randomness is confined to identity creation. Submit and acknowledge are the
only receipt frames, and resume replays by identity from a `ReceiptCursor`. The state
machine is sans-IO, and a scripted harness driver drops, duplicates, and reorders
frames.

## Dependencies

The manifest (7) declares retention horizons, reason codes, and error text.
Versioned writes (9) supply the `base_version` and conflict taxonomy. The policy
language (8) supplies `Rejected` with a rule identity. The scheduler (11) owns
per-key order. Enforcement (12) writes one audit record per verdict. The wire protocol (14) carries submit, acknowledge, and replay. The
replica (15) exposes `applied_version`. Projection (17) keeps the verdict
single-shard. The business event stream (24) emits in the same transaction. The
qualification suite (30) holds golden vectors.

## Acceptance criteria

1. Kill the process after enqueue and before send. The intent survives restart
   and is sent once.
2. Send one intent 1,000 times with drops and duplicates. The data changes once
   and every response carries the same receipt.
3. Submit one identity with two payloads. The authority returns
   `write.idempotency_key_reuse` and writes no data.
4. Inject a crash at every step of the commit. Data and receipt are both present
   at `commit_version` `v`, or both are absent.
5. Read with `applied_version` below `commit_version`. The receipt reads
   `Committed` and local visibility reads false.
6. Search and get while an intent is `Queued`. Neither returns the intent.
7. Cancel offline. The local outbox shows `Abandoned`. No receipt is created.
8. Age a receipt past the replay horizon. A duplicate submit returns
   `receipt.expired`, and the client re-reads.
9. Fill the outbox. The next intent returns `outbox.full` and no queued entry is
   lost.
10. Walk all state pairs. No path leaves a terminal state or enters `Queued`
    twice.

## What would falsify this design

- Data visible with no receipt after a crash.
- Any delivery order that applies one intent twice.
- A pending intent returned by search or get.
- A receipt that changes after `Committed` or `Conflict`.
- Retention shorter than the replay horizon, with a retry that re-executes a
  committed write.
- A fifth state, or a state name that changes before 1.0.

## Open questions

1. **Local close (settled).** A client must not write a terminal `Rejected` without an authority
   verdict. Cancellation is a local outbox disposition: `CancelRequested`, then `Abandoned`.
2. **Queued is live (settled).** A receipt has four lifecycle states. `Queued` is
   live and not terminal. `Committed`, `Rejected`, and `Conflict` are terminal.
3. **Cross-device handover.** Does a second replica of the same client inherit
   the outbox, or does each replica own its intents?
4. **Receipts as queryable data.** A system sub-namespace is simple and single-shard.
   A receipt table would let operators query by state, at the cost of policy and
   placement.
5. **Payload retention.** How long does the authority keep the payload for
   conflict explanation, as distinct from the deduplication digest?
